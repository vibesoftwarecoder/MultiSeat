**This release makes a seat's DPI scale actually reach Windows, which it never did before, and makes the wait for a seat's input desktop react to desktop switches as they happen.**

> DRAFT for 0.6.19. `version.txt` is not bumped here; delete this line when the release is cut.

## What was happening

### Seat scale reverts (#93)

Issue #93: with `FollowClientResolution` on, a client connecting at a different resolution resized the seat correctly, but the seat's DPI scale went back to 100% instead of staying at the value set in the dashboard.

MultiSeat wrote the seat's scale into `Default.rdp` as `desktopscalefactor`, and the dashboard, the API and the log all reported that value. None of them checked what Windows did with it. On the reference host it did nothing at all. A seat asked for 200%, and then for 150%, ran at 100% both times. That held after a reconnect, and it held in a session created from scratch.

The cause is in mstsc, the Remote Desktop client that creates each seat's session. mstsc reads `desktopscalefactor` and `devicescalefactor` from the file. It passes the scale on **only when both are set**. With either one missing, it sends the scale of the monitor its own window sits on, which is the host's console monitor. MultiSeat never wrote `devicescalefactor`. So every seat has always run at the console's scale, whatever the dashboard, `DefaultScaleFactor` or the width rule said. On a console at 100% that looks like "the scale reverts to 100%".

This was found by reading mstsc's own code (`mstsc.exe` and `mstscax.dll`, version 10.0.26100.9444). The RDP specification states the same rule for the data the client sends. In [MS-RDPBCGR 2.2.1.3.2](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpbcgr/00f1da4a-ee9c-421a-852f-c19f92343d73), desktopScaleFactor "MUST be ignored if it is less than 100% or greater than 500% or **deviceScaleFactor** is not 100%, 140%, or 180%."

The 0.6.19 draft had added a different fix. It logged the seat's session off and created it again whenever a reconnect did not apply the scale. The idea was that Windows applies a scale when it creates a session but not when it reconnects one. The live test above disproved that. The new session ran at the wrong scale too, and the recreate closed every program in the seat for nothing. That recreate is removed.

### Input desktop denied after logon (#96)

Issue #96: right after logon, a seat's input desktop can be denied for minutes while another program holds the Secure Desktop. 0.6.18 added a wait for the desktop to settle. That wait only polled four times a second, and nothing recorded what was actually on the Secure Desktop. The reporter's host pointed at a logon-time elevation prompt from ASUS Armoury Crate (`ArmourySocketServer.exe`), but that came from a separate trace.

## What changes

### Seat scale (#93)

- **`Default.rdp` now carries `devicescalefactor:i:100` beside `desktopscalefactor`.** That is what makes mstsc send the seat's scale. 100 is the neutral value; Windows uses the device scale only for Windows 8.1 store apps. The scale is sent the same way when a session is created and when it is reconnected.
- **Behaviour change on hosts whose console is not at 100%.** Until now every seat silently ran at the console's scale. From this release a seat runs at the scale MultiSeat picks for it: the seat's override, then `DefaultScaleFactor`, then the width rule (100% up to 1920 wide). If your seats looked right only because the console happened to be scaled, set `DefaultScaleFactor` or a per-seat scale.
- **The applied scale is read back from inside the session.** After every reconnect, MultiSeat reads the scale Windows is actually running the session at, per display, and logs it beside the scale it asked for. A mismatch is a warning in the service log.
- **A mismatch is reported, never acted on.** MultiSeat does not log a seat's session off over a reading. The draft's automatic recreate is gone.
- **The seat reports it.** `GET /api/seats/{id}/diagnostics/applied-scale` returns the reading beside the scale that was asked for, for every display. Seat status gains `appliedScaleFactor`, `scaleMismatch` and `scaleNote`. The dashboard shows "Running at N%" next to the scale when they differ, with the note under it. Run the diagnostic again after a client connects to see the scale of Apollo's virtual display, which a reading taken at reconnect time predates.
- **The note also covers the system scale.** Windows fixes a session's system scale when the user signs in. A later scale change moves the display's scale, which most programs follow, but programs that only read the system scale keep the old size until the seat user signs out and back in. When the reading shows that, the note says so. Signing out closes the seat's programs, so it is left to you.
- The health-check reconnect and provisioning record the same reading.

### Input desktop wait (#96)

- **The wait now listens for desktop switches.** Inside the seat session, the helper registers for Windows' desktop-switch event. When one arrives it re-tests the desktop at once and restarts the stable window, because a switch proves the desktop changed even if it is openable again by the time we look. A switch that lands in the last instant before the wait would finish also blocks it.
- **Polling stays as the backstop.** The 250 ms check still runs. If the event never fires, or the hook cannot be installed, the wait behaves exactly as in 0.6.18. The timeout, the 3-second stable window and the "start Apollo anyway, with a warning" outcome are unchanged. When the desktop is already accessible, nothing is different.
- **The service log reports it.** The "input desktop usable" and "still not usable" lines now include the number of desktop-switch events seen and whether the hook was installed.
- **The readiness probe records the switches.** With `DiagnoseInputDesktopReadiness` on, the JSONL file gains a `hook` line (did the hook install), one `desktop-switch` line per event (timestamp, the input desktop's name at that moment, and every desktop with the processes and windows on it), and an event count in the `summary`. `scripts/diagnose-issue96.ps1` reads the new lines and reports `HookInstalled` and `SwitchEvents` per trial.
- **Troubleshooting entry for the Armoury Crate trigger,** including the workaround ASUS guides describe (run the `ArmourySocketServer` task as SYSTEM). The workaround is unverified on the reference host.

## Who this affects

- **#93:** Anyone who sets a scale on a seat (through the dashboard, the API, or `DefaultScaleFactor`), or whose seats are wider than 1920 pixels (the width rule picks more than 100% there). Those settings had no effect before. Also anyone whose host console runs at a scale other than 100%: seats stop inheriting it.
- **#96:** Hosts where a seat's Apollo fails to open the input desktop right after logon. If your seats already start cleanly, nothing changes.

## How this was checked

### Seat scale (#93)

**The failure was measured on a live seat** (Windows 11 build 26100, console at 100%, one seat, 1920x1080). With the previous build, a seat set to 200% and then to 150% ran at 100% after the reconnect, and again after the draft's recreate made a new session. Three sources inside the session agreed: the DPI a program is given, the scale the display configuration stores, and the `AppliedDPI` Windows writes for the user at sign-in (96, which is 100%). The `Default.rdp` that mstsc loaded did contain `desktopscalefactor:i:150`. There is no Remote Desktop policy on that host that tells Windows to ignore the client's scale.

**The cause was found by reading mstsc's code,** not by trying things. Its file loader reads both scale keys with a default of 0. Its connect step passes them to the RDP control only when both are non-zero. The control accepts a device scale of 100, 140 or 180 only.

**Tests.** A model of that rule reproduces the live failure from the exact file the previous build wrote, and shows that the new file sends every allowed scale (100 through 500). Other tests check that a mismatch is logged and the session is kept, that a slow reading is retried before it counts, that an unreadable session is "unverified", and what the dashboard note says in each case. All of them were mutation-checked: removing `devicescalefactor`, giving it a value mstsc rejects, or breaking the note or the retry each fails a test.

**What this doesn't confirm:** the fixed build has not run on a live seat yet. Two things still need one. First, that the seat now runs at the requested scale. The diagnostic will show it: the RDP display's effective scale should equal the intended one. Second, whether a reconnect also moves the system scale or only the display's scale. If you are affected, please run `GET /api/seats/{id}/diagnostics/applied-scale` after setting a scale and after a client-triggered resize, and share the output on #93.

### Input desktop wait (#96)

The wait logic is covered by tests that use a fake clock and a scripted event source: an event proceeds without waiting for the next poll, no events still proceeds by polling, a timeout still starts Apollo, a switch restarts the stable window, and a flood of events cannot push the wait past its timeout. The tests were mutation-checked.

**What this doesn't confirm:** whether Windows delivers desktop-switch events to a non-SYSTEM process in an RDP seat session for Winlogon switches. No test can show that, and it was not run on a live seat for this draft. Turn on the probe on an affected host and read the `hook` line and the `EventCount` in the summary. If the count stays at 0 while samples show the desktop denied, the polling backstop did the work and the event adds nothing on that host.

## Known limitations

- **Seats capture the remote desktop surface, not a dedicated virtual display.** A Windows constraint, not a regression.
- **The seat refresh rate is one value for the whole host**, not one per seat.
- **`Ready` does not mean capture is active.** Capture begins when a client connects.
- **A scale change on a live seat moves the display's scale but may not move the session's system scale** until the seat user signs out. Programs that only read the system scale keep their old size until then. The dashboard says when this is the case.
- **If a third-party prompt holds the Secure Desktop longer than `WaitForInputDesktopSeconds`,** Apollo still starts after the timeout and may fail. Removing the prompt is the cure.
