**A seat's scale setting is now checked after a reconnect, and the session is created again when Windows did not apply it. This fixes the scale reverting to 100% after a client-triggered resolution change.**

## What was happening

Issue #93: with `FollowClientResolution` on, a client connecting at a different resolution resized the seat correctly, but the seat's DPI scale went back to 100% (or the width-derived value) instead of staying at the value set in the dashboard.

MultiSeat did carry the seat's scale into the connection settings. The code path was checked end to end: the follower, the resolution change, the health-check reconnect and a fresh provision all build their settings from the same function, and all of them include the seat's scale. What was missing was any check of what Windows did with it.

A resolution change reconnects to the seat's existing Windows session. That a reconnect applies a new **size** was measured. That it applies a new **scale** never was, and the setting's own code comment said so. The dashboard, the API and the log all reported the scale MultiSeat *asked for*, so a session that ignored the request looked exactly like one that took it.

## What changes

- **The applied scale is read back from inside the session.** After every reconnect, MultiSeat reads the scale Windows is actually running the session at, per display, and logs it beside the scale it asked for. A mismatch is a warning in the service log.
- **If the reconnect did not apply the scale, the session is created again.** MultiSeat logs the session off, waits until it is gone, creates it at the right scale, and sets it up again the way the health check does after a recreate (Apollo, display isolation, the audio and input settings that belong to a session). **Programs running in the seat are closed when this happens.** It happens only when the reading shows the wrong scale after a few seconds, never when the reconnect took, and at most once per change. If the new session is still at the wrong scale, MultiSeat says so and stops rather than looping.
- **A reading that cannot be taken never causes a recreate.** The seat is reported as unverified and left alone.
- **The seat reports it.** `GET /api/seats/{id}/diagnostics/applied-scale` returns the reading beside the scale that was asked for, for every display. Seat status gains `appliedScaleFactor` and `scaleMismatch`, and the dashboard shows "Running at N%" next to the scale when they differ. Run the diagnostic again after a client connects to see the scale of Apollo's virtual display, which a reading taken at reconnect time predates.
- The health-check reconnect and provisioning record the same reading. They never recreate a session over it: a session that dropped by itself keeps the scale it had.

## Who this affects

Anyone who sets a scale on a seat (through the dashboard, the API, or `DefaultScaleFactor`) and also uses `FollowClientResolution`, or changes a live seat's scale. If you never change a seat's scale or resolution after it is created, nothing changes.

## How this was checked

The new tests cover the decision and its order: the recreate follows a mismatch that lasted, never follows a reconnect that took, happens once, and creates the new session only after the old one is gone. A live cross-check compares the DPI an application is given with the scale the display configuration stores. The reader was run on a console session and agreed with the display configuration there.

**What this doesn't confirm:** none of this was run on a live seat. Two things need one. First, that a reconnect really leaves the scale unchanged (the diagnostic exists to show that, and the recreate only runs if it does). Second, that the scale read from the RDP display is the one a client sees through Apollo's virtual display. If you are affected, please run `GET /api/seats/{id}/diagnostics/applied-scale` before and after a client-triggered resize and share the output on #93.

## Known limitations

- **Seats capture the remote desktop surface, not a dedicated virtual display.** A Windows constraint, not a regression.
- **The seat refresh rate is one value for the whole host**, not one per seat.
- **`Ready` does not mean capture is active.** Capture begins when a client connects.
- **A recreate closes the programs running in the seat.** It is the only way to apply a scale Windows will not take on a reconnect.
