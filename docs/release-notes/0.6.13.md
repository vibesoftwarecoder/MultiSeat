**This release adds a host-wide refresh-rate setting so seats can run faster than the old fixed 62Hz, and closes a gap where the API could create a Windows account with a blank password.**

## What was happening

Two separate problems prompted this release.

Issue #74: a seat's real frame rate is capped by one Windows setting, `DwmFrameIntervalMs`, that is shared by every seat on the host. It defaulted to 16ms, about 62Hz, and the only way to change it was to hand-edit a config file.

Issue #76: creating a seat account through the API accepted a blank password with no error, and went ahead and created a real Windows account with that blank password.

## What changes

**Host refresh-rate setting (#74).** The shared refresh rate is now settable from the dashboard, with a new Refresh Rate control, or from the API with `GET`/`POST /api/system/refresh-rate`, among four values that were each measured safe: 30Hz, 62Hz, 125Hz, and 166Hz. The shipped default moves from 16ms (~62Hz) to 8ms (~125Hz). That default is backed by a live measurement under real game-like load, not a guess: it costs about +15% of one CPU core per busy seat, which is roughly +0.6% of a 24-core host. A change only takes effect the next time a seat starts a session, not one already running. A host upgrading from an earlier version keeps its existing setting (16ms) unchanged, because the installer preserves `appsettings.json` byte for byte on purpose. Only a fresh install, or using the new dashboard or API control, gets the new 8ms default.

**A security fix (#76).** Creating a seat account through the API no longer accepts a blank password. An empty, null, or whitespace-only password is rejected with a clear error before any account is created.

## Who this affects

For #74: anyone who wants a shared refresh rate higher or lower than the old fixed 62Hz default, especially someone streaming to a high-refresh-rate client. For #76: anyone creating seat accounts through the API directly, rather than through the dashboard, which already always supplied a password.

## How this was checked

For #74: 689 tests pass, 24 of them new. It was also live-verified end to end on a real host: the API call, the registry write with no service restart needed, and a freshly provisioned seat actually composing at the new measured rate — 125.3 fps measured against a mathematical prediction of 125.

For #76: 703 of 720 tests pass, with new cases added for the fix. It was live-verified that a rejected password creates zero Windows accounts, and that a valid password still creates an account normally.

Both fixes were mutation-checked: each new test was confirmed to fail if its fix were reverted, not just written to pass.

Found while fixing #76, and filed separately as #77, not fixed here: deleting an account through the API doesn't remove its Windows profile directory. That likely explains several old stale profile folders found on this host during testing.

## Install

```powershell
.\prerequisites\install-prerequisites.ps1     # drivers - needed either way
.\scripts\install-service.ps1 -FromZip .
```

Your configuration is preserved, as of 0.6.4 — `appsettings.json` and `appsettings.local.json` are
kept byte for byte, with a backup under `C:\ProgramData\MultiSeat\config-backups\`.

Afterwards, confirm what landed:

```powershell
& 'C:\Program Files\MultiSeat\MultiSeat.Service.exe' --config
```

It should report `0.6.13`.

## Known limitations

- **Seats capture the remote desktop surface, not a dedicated virtual display.** A Windows
  constraint on where a virtual display can attach, not a regression.
- **The seat refresh rate is one value for the whole host**, not one per seat.
- **Tearing a seat down still briefly disturbs a standalone Apollo.**
- **An Apollo that dies before it starts logging can still explain nothing** unless you run
  ApolloVibe `v2026.6.1-ms4` or later, which writes `sunshine-startup-error.log` on an early
  startup failure.
- **Setting a seat's DPI scale override from the dashboard is not built yet.** Use the API
  (`POST /api/seats` or `POST /api/seats/{id}/scale`) directly.
- **Deleting an account through the API doesn't remove its Windows profile directory or
  `ProfileList` registry entry.** Filed as #77, not fixed here.
