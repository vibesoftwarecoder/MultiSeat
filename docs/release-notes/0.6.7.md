**A seat's refresh rate is selectable again, and seats are no longer stuck composing at about 32
frames per second. If your seats felt choppy, this is the release to take.**

## What was happening

A seat does not stream a dedicated virtual display. It streams the surface of its RDP session, so
that session's display is what a game inside the seat sees, and its composition rate is the ceiling
on how often the seat can produce a new frame.

Windows sets both from one registry value, `DWMFRAMEINTERVAL`. The rate is `1000 / interval`.
MultiSeat has written that value since the first release, and it wrote **1** — which is where the
seat's long-documented 1000 Hz display came from. `1000 / 1`. That worked, and it is why seats could
stream well above the 30 fps Windows gives an RDP session by default.

It does not work now. On current Windows an interval below 2 is out of range, so Windows ignores it
and composes at its own default instead. Nothing fails, nothing is logged, and reading the value
back still returns the 1 that was written — so the service reported the setting applied, every
start, while seats sat at about 32 fps. A seat streaming at 60 fps was sending roughly every second
frame twice.

We cannot date when Windows changed, only show that it has.

## What was measured

One fresh RDP session per value, because the compositor reads the interval when a session starts.
The composition rate was sampled from inside the session by pacing off `DwmFlush`. The advertised
refresh was read from both sides: GDI `EnumDisplaySettings`, and the CCD side that DXGI and games
agree with. **At every interval the two agreed exactly.**

| `DWMFRAMEINTERVAL` | display advertises | composition measured |
|---|---|---|
| not set | 32 Hz | 32.0 fps |
| **1** — what MultiSeat shipped | 32 Hz | **31.9 fps** (ignored; same as not set) |
| 2 | 500 Hz | 464.7 fps |
| 6 | 166 Hz | 165.4 fps |
| 8 | 125 Hz | 125.2 fps |
| **16** — the new default | **62 Hz** | **62.1 fps** |
| 33 | 30 Hz | 30.0 fps |

## What changes

The interval is now a setting, **`MultiSeat:DwmFrameIntervalMs`**, and it defaults to **16** — a
62 Hz display, which covers the 60 fps a seat is provisioned at by default and looks like an
ordinary monitor rather than the 1000 Hz that older titles refused to run on.

Pick it for the fastest client the host serves:

| target | interval | you get |
|---|---|---|
| 30 fps | 33 | 30 Hz |
| 60 fps | **16** | 62 Hz |
| 120 fps | 8 | 125 Hz |
| 144 fps | 6 | 166 Hz |

Exact 60 and 144 are not reachable, because the interval is a whole number of milliseconds and
neither `1000/60` nor `1000/144` is one. Interval 7 would advertise 142 Hz, just under a 144 Hz
client, so 6 is the value that covers it.

**A value below 2 is refused and logged as a warning rather than written**, because writing one
reports success and changes nothing — which is exactly how this went unnoticed. The startup log line
now names the rate the interval produces instead of claiming a high frame rate without saying what
it is.

This takes effect on sessions created after the service starts, so restart the service and
re-provision a seat to pick it up.

## One limit worth knowing

`DWMFRAMEINTERVAL` is machine-wide. **Every seat on a host shares one value**, and all seats share
the one RDP listener, so there is no per-seat split to exploit. A host running one seat at 60 fps
and another at 120 fps sets the interval for the faster one; the slower seat simply has headroom.

## A note on earlier findings

Work in June 2026 concluded that a seat's display was locked to a single 1920x1080@1000 mode, and
that changing its refresh through GDI returned success while DXGI carried on reporting 1000 Hz. That
was true on the Windows build it was measured on. It is not true on the current one: both sides now
report the same rate, and both follow this setting. The rest of that finding stands — a seat still
captures its RDP session surface, and that is still a Windows constraint rather than a regression.

## How this was checked

Five new tests, and all 565 pass in CI. They assert that the shipped interval is one Windows
honours, that the C# default and `appsettings.json` agree, and that the old value of 1 sits below
the floor — so restoring it fails the suite instead of shipping quietly again. The suite was also
run with the default put back to 1, to confirm those tests fail rather than pass vacuously.

The measurements above were taken on the reference host with the probe now shipped as
`scripts\probe-dwm-rate.ps1`. It reports `PROBE INVALID` rather than a number when `DwmFlush` does
not actually block, so a reading that was never earned is not presented as a result.

**Not checked end to end.** These are measurements of the session's compositor and of what its
display advertises, not of a live Moonlight stream. No client stream was measured for this release.
The CPU cost in TermService and DWM at the shorter intervals was not measured either, which is the
reason the default is 16 rather than something faster.

## Install

```powershell
.\prerequisites\install-prerequisites.ps1     # drivers - needed either way
.\scripts\install-service.ps1 -FromZip .
```

Your configuration is preserved, as of 0.6.4 — `appsettings.json` and `appsettings.local.json` are
kept byte for byte, with a backup under `C:\ProgramData\MultiSeat\config-backups\`.

Because your `appsettings.json` is kept, a host upgrading from an older release will not have
`DwmFrameIntervalMs` in its file. That is fine: the built-in default applies, and the installer
lists settings a release adds that your file lacks.

Afterwards, confirm what landed:

```powershell
& 'C:\Program Files\MultiSeat\MultiSeat.Service.exe' --config
```

It should report `0.6.7`.

## Known limitations

- **Seats capture the remote desktop surface, not a dedicated virtual display.** A Windows
  constraint on where a virtual display can attach, not a regression.
- **The refresh rate is one value for the whole host**, not one per seat. See above.
- **Tearing a seat down still briefly disturbs a standalone Apollo.** Announced rather than silent,
  but unchanged.
- **This release does not fix what makes Apollo exit in #54.**
