**About 27.8 hours after a seat was provisioned, its session anchor expired and the service began logging the same warning every 5 seconds. This release relaunches the anchor and reports an exit once.**

## What was happening

Each seat session holds a hidden anchor process, `timeout.exe /t 99999 /nobreak`. Its job is to keep Windows from reclaiming an empty session.

99999 seconds is 27.8 hours. The old code comment said about 11.5 days, which was wrong.

About 27.8 hours after a seat was provisioned, the anchor exited. From then on the service logged `Session anchor for session N exited, but WTS session is still active` at Warning level every 5 seconds. It never relaunched the anchor.

On one host this produced 1,735 warnings in a day for a single session. That filled the 20 MB circular Application log and pushed older diagnostics out of it.

The seat itself kept working. The hidden console-side `mstsc` keepalive holds the session Active on its own. What was lost was a redundant safeguard, and the log.

## What changes

**The health check now relaunches the anchor when the session is still Active.** It takes the seat's lifecycle gate first and checks the seat again before it launches anything. If a reconnect holds the gate and the wait times out, the health check tries again on the next 5-second check.

**An anchor exit is reported once per anchor.** It is no longer repeated every 5 seconds.

**An anchor that dies within 10 minutes is reported once and not relaunched.** This means nothing that keeps killing the anchor can cause a storm of new processes.

**Teardown still kills the anchor, and now also closes its process handle.** The old code leaked that handle.

## Why the anchor is relaunched instead of never expiring

The earlier alternatives to `timeout.exe` (`cmd /c pause`, `cmd /k`, `waitfor` and PowerShell) failed inside RDP sessions. `ping` worked, but it generates network traffic. `timeout.exe` is the known-good shape, so the service relaunches it instead.

## Who this affects

Any seat that stays provisioned longer than about 27.8 hours. Nobody needs to do anything. The warnings stop and the anchor comes back.

On older versions, you can reprovision the seat or restart the service to restart the clock. The warnings only cost log space.

## How this was checked

602 unit tests pass, and the Release build has 0 errors. Ten of the tests are new. They cover the anchor tracker and the order of the relaunch steps, including one simulated day of 5-second checks and a gate timeout.

The real relaunch through `CreateProcessAsUser`, and the wiring between the health check and the launcher, are not covered by any test and have not run on a real seat. The first real relaunch happens about 27.8 hours after a seat is provisioned on this build.

## Install

```powershell
.\prerequisites\install-prerequisites.ps1     # drivers - needed either way
.\scripts\install-service.ps1 -FromZip .
```

Your configuration is preserved, as of 0.6.4 — `appsettings.json` and `appsettings.local.json` are
kept byte for byte, with a backup under `C:\ProgramData\MultiSeat\config-backups\`.

Afterwards, confirm what landed:

```powershell
& 'C:\Program Files\MultiSeat\MultiSeat.Service.exe' --config
```

It should report `0.6.11`.

## Known limitations

- **Seats capture the remote desktop surface, not a dedicated virtual display.** A Windows
  constraint on where a virtual display can attach, not a regression.
- **The seat refresh rate is one value for the whole host**, not one per seat.
- **Tearing a seat down still briefly disturbs a standalone Apollo.**
- **An Apollo that dies before it starts logging can still explain nothing** unless you run
  ApolloVibe `v2026.6.1-ms4` or later, which writes `sunshine-startup-error.log` on an early
  startup failure.
