**On a clean install, seats could fail to provision outright — and leave no log explaining why.
If you have installed MultiSeat recently and never got a seat to start, this is the release to
take.**

## What was happening

A seat failed at **Configuring** with `Apollo exited before its serverinfo API became ready`, and
the error pointed at a seat log, `C:\ProgramData\MultiSeat\apollo\<account>\apollo.log`, that was
never created. Apollo launched, ran for about ten seconds, and exited on its own. Nothing was
written anywhere.

The cause was one missing line in the config MultiSeat generates for each seat.

MultiSeat already gives every seat its own `apps.json`. It copies one into
`C:\ProgramData\MultiSeat\apollo\<account>\config\`, strips the entries that only make sense for the
console install, and grants the seat account permission to write it. What it never did was tell
Apollo to read that file.

Left unset, Apollo resolves its app list to `config\apps.json` **inside its own install directory**,
under `C:\Program Files`. If that file does not already exist, Apollo tries to create it there by
copying its own `assets\apps.json`. A seat runs as a standard Windows user, which has read-only
access to `Program Files`, so the copy fails — and it fails early enough that Apollo has not started
logging yet. The process exits with nothing written, which is why there was no log to read.

## Why it took this long to find

The file only has to exist once. On any host where Apollo has been run with administrator rights —
which happens the first time someone opens it from the Start Menu — `config\apps.json` is already
there, and every seat provisioned afterwards reads it happily.

On the reference host that file was created on 2026-08-14, so this bug was invisible here for
weeks while seats provisioned normally. It took a clean install to surface it.

## What changes

The generated `sunshine.conf` now sets `file_apps` to the seat's own copy, alongside the
`file_state` and `credentials_file` overrides that were already there for the same reason: Apollo
resolves relative paths against its install directory, which every instance shares, so anything a
seat must own needs an absolute path.

Two things follow from that:

- **A seat no longer touches `Program Files` for its app list**, so a clean install works without
  anyone having run Apollo as an administrator first.
- **Each seat gets its own app list**, instead of every seat sharing one file in the install
  directory. That is what the per-seat copy was always meant to do.

## If you are hitting this today

The workaround still works and does not need this release. From an elevated PowerShell:

```powershell
New-Item -ItemType Directory -Force "C:\Program Files\ApolloVibe\config" | Out-Null
Copy-Item "C:\Program Files\ApolloVibe\assets\apps.json" "C:\Program Files\ApolloVibe\config\apps.json"
```

Then tear the seat down and provision it again. After upgrading to 0.6.8 it is no longer needed,
though leaving the file in place does no harm.

## How this was checked

Two new tests, and all 567 pass in CI: `file_apps` must be present, must point at a file that
exists, and must sit inside the seat's own directory; and it must never be under `Program Files`.
Both fail if the fix is removed.

⚠️ **Not verified on a clean install.** The reference host is one where the old bug cannot
reproduce, because the file in `Program Files` has been there since August. The fix is verified by
tests and by reading the generated config; it has not been run on a machine that reproduces the
original failure. Confirmation from anyone installing fresh is welcome.

The first version of one of those tests had the same flaw as the bug — it asserted the seeded file
exists, which is only true on a machine with Apollo installed, so it passed locally and failed in
CI. It now builds a stand-in install of its own, and is independent of what happens to be on the
machine running it.

## Install

```powershell
.\prerequisites\install-prerequisites.ps1     # drivers - needed either way
.\scripts\install-service.ps1 -FromZip .
```

Your configuration is preserved, as of 0.6.4 — `appsettings.json` and `appsettings.local.json` are
kept byte for byte, with a backup under `C:\ProgramData\MultiSeat\config-backups\`.

Afterwards, confirm what landed:

```powershell
& 'C:\Program Files\MultiSeat\MultiSeat.Service.exe' --config
```

It should report `0.6.8`.

## Known limitations

- **Seats capture the remote desktop surface, not a dedicated virtual display.** A Windows
  constraint on where a virtual display can attach, not a regression.
- **The refresh rate is one value for the whole host**, not one per seat.
- **Tearing a seat down still briefly disturbs a standalone Apollo.**
- **An Apollo that dies before it starts logging still explains nothing.** This release removes one
  cause of that; it does not make the class of failure visible. That belongs in Apollo itself and is
  tracked separately.
