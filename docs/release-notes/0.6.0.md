**This is the first MultiSeat release that ships an actual binary.**

Every release from v0.2.0 to v0.5.1 had zero assets. Installing meant cloning the repository and
building it, which required the .NET 9 SDK and Node 20+ on the machine you wanted to stream from.
That is a lot to ask of a gaming host, and it made "please try the latest version" a much bigger
request than it sounded.

## Install

Download `multiseat-windows-x64.zip` below, then:

```powershell
.\scripts\install-service.ps1 -FromZip .\multiseat-windows-x64.zip
```

**The asset is self-contained.** It needs no .NET SDK, no .NET runtime and no Node. You still need
the drivers from `.\prerequisites\install-prerequisites.ps1` — those are required either way.
Everything else the installer does, including RDP configuration, certificates and service
registration, is identical to a build from source.

The installer checks the zip before it touches an existing install, so a truncated or wrong
download cannot leave you with neither the old version nor a working new one. It also refuses a zip
that is not self-contained rather than half-installing something that would then need a runtime.

Building from source still works exactly as before, and is the right path if you are developing
MultiSeat or want a build of a commit with no release.

## Why the download is 53 MB

A framework-dependent build would be 7.9 MB, but it requires both `Microsoft.NETCore.App` and
`Microsoft.AspNetCore.App`. That means installing the **ASP.NET Core Runtime** specifically — not
the plain .NET Runtime, and not the Desktop Runtime, all three of which Microsoft offers on the
same download page. Picking the wrong one fails in a way that is hard to diagnose from the outside.
Bundling the runtime costs 46 MB and removes that whole class of problem.

## The version number now means something

Releases used to be tagged `v0.5.1` while the binary reported `1.0.0`, so the version a host told
you about matched no release that existed. The version now comes from one file, `version.txt`, and
the release workflow refuses to publish when the git tag and that file disagree.

To ask a host what it is actually running:

```powershell
& 'C:\Program Files\MultiSeat\MultiSeat.Service.exe' --config
```

That prints the deployed version and commit, when the binary was deployed, and every setting with
the value that binary resolved. It is the fastest way to answer "did my update actually take", and
worth running before reporting a bug.

## Also in this release

- **A gated diagnostic for the console cursor leak** (issue #18): `scripts\diagnose-issue18.ps1`.
  It checks the deployed binary and the seat's age before it measures anything, so it cannot report
  a result about a build that was never deployed.

## Known limitations

- Keyboard/mouse isolation (`EnableKeyboardMouseIsolation`) remains **off by default and is a
  no-op**. The hooks run in session 0, where the filter cannot see seat input. Turning it on now
  logs a warning saying so rather than implying it works.
- This release has been verified by CI, which builds the zip and checks its contents. The
  `-FromZip` install path has been tested against good and deliberately broken zips, but not yet on
  a fresh host. If you hit something, please open an issue with the output of `--config`.
