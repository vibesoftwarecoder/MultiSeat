**This release makes the source-build installer safe on a host whose install folder was once self-contained, and makes both install paths replace the folder the same way.**

## What was happening

`scripts\install-service.ps1` built from source with `dotnet publish` straight into `C:\Program Files\MultiSeat`. `dotnet publish` copies `MultiSeat.Service.runtimeconfig.json` only when the source file is newer than the one already there. On a folder that had been self-contained, that left a hybrid: a framework-dependent `runtimeconfig.json` beside the old `hostfxr.dll`. The host then looked for a bundled runtime the config no longer declared, and the service failed to start with `No frameworks were found` (service control manager errors 7000 and 7009 after a 30 second timeout). It looked like a missing .NET runtime. The host had one installed.

The first publish onto such a folder could also pass by accident. The old self-contained config was newer, so it survived, and the new files ran on the leftover bundled runtime. Only a later publish broke it.

## What changes

- **The source build no longer publishes into the install folder.** It builds into a temporary staging folder (service, dashboard, InputHook DLL), checks it, and then uses the same routine `-FromZip` uses to replace the install folder as a whole.
- **The staged payload is checked before anything is touched:** `MultiSeat.Service.exe`, `appsettings.json`, `wwwroot\index.html`, and a runtime layout that agrees with itself. A payload is consistent when `hostfxr.dll` is present exactly when `runtimeconfig.json` has `includedFrameworks`, and a framework-dependent payload carries no bundled runtime files. The installed folder gets the same check after the copy. A mismatch fails with the exact reason.
- **A source build checks the host's shared runtimes first.** It reads the frameworks the built `runtimeconfig.json` demands (`Microsoft.NETCore.App`, `Microsoft.AspNetCore.App`) and compares them with the host's .NET install under the normal roll-forward rules. If one is missing, the installer stops **before** it stops the service, and says what to install or to use `-FromZip` instead.
- **The service is stopped only after that.** If the copy fails, the installer puts the previous folder back from a full backup and starts the service again if it was running.
- **New backup:** a full copy of the old install folder in `C:\ProgramData\MultiSeat\install-backups\<timestamp>`. The newest three are kept.
- **Both backup folders are now private.** `config-backups` and `install-backups` hold copies of `appsettings.local.json`, which can carry the API key. They inherited ProgramData's permissions, so any standard user on the host could read them. They are now limited to SYSTEM, Administrators and the account that ran the installer. Existing `config-backups` from earlier installs are covered too.
- **Behaviour change for source builds:** your `appsettings.json` and `appsettings.local.json` are now kept byte for byte, as `-FromZip` already did. A newer `appsettings.json` in the repo no longer replaces yours. Settings the build adds that your file lacks are listed during the install.
- **The "this release adds settings" list now works on Windows PowerShell 5.1.** It could not parse the `//` comment lines in the shipped `appsettings.json` and printed the whole file as an error note instead.
- The release asset check now also requires `scripts\lib\install-lib.ps1`, which the installer loads.

## New: optional update notifications (off by default)

MultiSeat can now tell you on the dashboard when a newer MultiSeat, ApolloVibe or MoonlightVibe release exists. It is **off** unless you turn it on, because it is the first time the service would contact the internet. If you turn it on (`"UpdateCheckEnabled": true` in `appsettings.local.json`, or the switch on the System page), the service asks `api.github.com` for each project's release list about every 12 hours (`UpdateCheckIntervalHours`). It sends a generic User-Agent and nothing about your host. It never downloads or installs anything; it shows the release link, and you update by hand (see "Updating" in the README). Details: `docs/security-posture.md`, "Outbound connections". MoonlightVibe runs on your other devices, so MultiSeat cannot tell which version they have; it only shows the latest release.

If you upgrade with `install-service.ps1 -FromZip`, your existing `appsettings.json` is kept, so the new options are named by the installer and **nothing changes until you opt in**.

- New endpoints, all behind the API key when authentication is on: `GET /api/system/updates`, `POST /api/system/updates/check` (at most once a minute) and `POST /api/system/updates/settings`.
- Turning checks on or off, by file or from the dashboard, takes effect without a restart.
- The last result is cached in `C:\ProgramData\MultiSeat\update-check.json`, readable only by SYSTEM and Administrators. It is safe to delete.
