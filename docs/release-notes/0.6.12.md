**Streaming to an iPad Pro or iPhone had no custom resolution option, looked stuck at 60 fps, and showed a small, zoomed-out desktop — none of it a platform limit. This release adds a custom resolution option, a live resize control, a DPI scale override, and a warning when a chosen fps can't reach the host's refresh rate.**

## What was happening

Issue #70, reported by RageMC, described three problems streaming to an iPad Pro and an iPhone. There was no way to ask for a custom resolution. The fps seemed stuck at 60 no matter what was picked. And the desktop looked zoomed out and small on the tablet's screen. None of these came from a limit in Moonlight, Apollo, or the platform. The dashboard simply did not expose settings the backend already had, and the desktop's DPI scale had no way to account for a tablet's own high-DPI rendering.

## What changes

**Custom resolution and a live resize control.** The New Seat form now has a Custom option next to the six presets, so you can enter any width and height the backend already accepted, from 640x480 up to 8192x8192. The seat card also gets a live Resize control for a seat that is already running, using the resize API endpoint that existed before this release too.

**A DPI scale override.** Until now, a seat's scale came only from its width, a rule tuned for monitors, not tablets. You can now set a scale on one seat, or a host-wide default that every seat without its own setting falls back to; if neither is set, the old width-based guess still applies. It can be set at seat creation or changed live through a new `/scale` endpoint, and it survives autostart. The seat card shows the scale in effect today, but only as a read-only value — setting it from the dashboard is a follow-up, not part of this release. For now, set or change it through the API: `POST /api/seats` when creating a seat, or `POST /api/seats/{id}/scale` on one that is already running.

**A warning when your fps choice can't reach the client.** A seat's real frame rate is capped by the host's Windows composition rate, which defaults to about 62Hz and is shared by every seat on the host. The fps picker only changed what Apollo advertises to the Moonlight client, and nothing checked that number against what the host could actually compose, so a high fps choice was silently capped with no explanation. Provisioning now compares the two and logs a warning, and returns it in the API response, whenever they do not match.

## Bugs found while building this

Building and live-testing the features above turned up four bugs. All of them existed before this release; this work simply exercised them harder.

- **A resize or scale change never waited for the old session to actually disconnect before relaunching it.** It only looked correct before, because a health check rescued the seat 3.5 to 7 seconds later, at the cost of two extra Apollo restarts. It now waits for the disconnect properly, and a resize or scale change completes directly in about 7 seconds.
- **That same health check had its own race.** It could see the session mid-reconnect, wait for the seat's lifecycle gate, and then restart Apollo again even though the resize had already finished correctly. It now checks the session's state again after taking the gate, and leaves a seat alone once it sees the reconnect already succeeded.
- **Both of those bugs logged misleading lines.** One said "attempting restart" when nothing had restarted. The other logged a Warning for an expected disconnect that read exactly like a real, unexplained one. Both now log accurately.
- **A divide-by-zero.** The new fps warning computed the host's refresh rate by dividing 1000 by `DwmFrameIntervalMs` directly, so a host misconfigured with that value at 0 would have crashed every seat provision. It now falls back to the same measured ~32fps default the rest of the code already assumes below the honored floor.

## Who this affects

Anyone who wants a resolution or DPI scale the six presets do not cover — a tablet like an iPad Pro is the case that prompted this — or anyone who wants to know why a chosen fps is not reaching the client. Existing seats and configs are unaffected unless you use the new custom resolution, resize, or scale features.

## How this was checked

665 unit tests pass, 67 of them new, 0 failures, and 17 skipped as before because they need real hardware. The dashboard build and its typecheck both pass.

Every fix in this release was also verified live on a real host, across five separate deploy-and-reverify rounds. That is a stronger bar than 0.6.10 or 0.6.11 held their own fixes to, and it is worth saying plainly. The live rounds included mutation checks, where each new test was confirmed to fail if its fix were reverted, and a real Moonlight client connecting and confirming that a resolution change and a scale change both took visible effect.

To be honest about what this did not cover: the resolution, scale, and fps-warning features themselves were live-tested through the API and a real client. `FollowClientResolution`, the pre-existing setting mentioned above that auto-matches a connecting client's resolution, was not itself live-tested in this release.

## Install

```powershell
.\prerequisites\install-prerequisites.ps1     # drivers - needed either way
.\scripts\install-service.ps1 -FromZip .
```

Your configuration is preserved, as of 0.6.4 — `appsettings.json` and `appsettings.local.json` are
kept byte for byte, with a backup under `C:\ProgramData\MultiSeat\config-backups\`.

Afterwards, confirm what landed:

```powershell
& 'C:\Program Files\MultiSeat\MultiSeat.Service.exe' --config
```

It should report `0.6.12`.

## Known limitations

- **Seats capture the remote desktop surface, not a dedicated virtual display.** A Windows
  constraint on where a virtual display can attach, not a regression.
- **The seat refresh rate is one value for the whole host**, not one per seat.
- **Tearing a seat down still briefly disturbs a standalone Apollo.**
- **An Apollo that dies before it starts logging can still explain nothing** unless you run
  ApolloVibe `v2026.6.1-ms4` or later, which writes `sunshine-startup-error.log` on an early
  startup failure.
- **Setting a seat's DPI scale override from the dashboard is not built yet.** Use the API
  (`POST /api/seats` or `POST /api/seats/{id}/scale`) directly.
