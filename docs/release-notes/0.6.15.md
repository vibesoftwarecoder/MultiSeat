**This release fixes a brand-new seat account's first logon, which could fail seat provisioning with input-desktop errors.**

## What was happening

Issue #80: a brand-new seat account's first logon could fail seat provisioning with `Failed to Open Input Desktop`/`DuplicateOutput() test failed`. Two things caused this together. Windows shows a privacy-settings screen on a truly fresh account's first logon. Separately, `LogonUI.exe` holds the input desktop for the whole first-logon sequence, and Apollo had no awareness of that.

## What changes

Two parts, building on each other.

**The privacy-settings screen is suppressed for new MultiSeat-managed accounts only.** The blocking screen is Windows' privacy-settings screen (`CloudExperienceHost`/`NTHPRIVACY`), not a Microsoft-account prompt. It is now suppressed by a registry value written into the new account's own hive before its first logon. `roelb`, `Gaming`, the Default profile, and machine policy are all unaffected.

**Provisioning now waits for LogonUI to actually leave a seat's session before starting Apollo.** The screen fix alone didn't close the race: `LogonUI.exe` holds the input desktop regardless, and Apollo had no awareness of that. The wait is capped at 15 seconds, with a safe fallback to start Apollo anyway if the cap is hit, instead of starting Apollo blind.

## Who this affects

Anyone provisioning a brand-new seat account for the first time. Existing accounts on their second or later logon are essentially unaffected, since the wait returns almost immediately when LogonUI isn't there to wait for.

## How this was checked

This was verified with real measured before/after numbers across two full rounds of live testing, not just built and assumed. With only the privacy screen suppressed, a fresh account's first logon still produced 18-21 Apollo input-desktop errors over 5.5-6.2 seconds. With both fixes, three separate fresh accounts each produced exactly 0 errors. Apollo's API came up in 2.6-3.6 seconds instead of 8-9.

The honest tradeoff: first-logon provisioning is about 1.9 seconds slower on average as a result (22-23s vs ~20s), because Apollo's startup no longer overlaps the tail of LogonUI's block - it correctly waits for it instead.

722 tests pass (16 new), 0 failures. Both changes are mutation-checked - each new test was confirmed to fail when its fix is reverted.

One honest limitation: the original report's actual failure - a roughly 28-second block ending in a 30-second provisioning timeout - never reproduced in either round of live testing, fixed or not. This closes a real, measured blocking mechanism, not a confirmed fix for a reproduced timeout.

## Install

```powershell
.\prerequisites\install-prerequisites.ps1     # drivers - needed either way
.\scripts\install-service.ps1 -FromZip .
```

Your configuration is preserved, as of 0.6.4 — `appsettings.json` and `appsettings.local.json` are
kept byte for byte, with a backup under `C:\ProgramData\MultiSeat\config-backups\`.

Afterwards, confirm what landed:

```powershell
& 'C:\Program Files\MultiSeat\MultiSeat.Service.exe' --config
```

It should report `0.6.15`.

## Known limitations

- **Seats capture the remote desktop surface, not a dedicated virtual display.** A Windows
  constraint on where a virtual display can attach, not a regression.
- **The seat refresh rate is one value for the whole host**, not one per seat.
- **Tearing a seat down still briefly disturbs a standalone Apollo.**
- **An Apollo that dies before it starts logging can still explain nothing** unless you run
  ApolloVibe `v2026.6.1-ms4` or later, which writes `sunshine-startup-error.log` on an early
  startup failure.
