**0.6.8 did not fully fix seats failing to provision on a clean install. This release does. If a seat
still fails at Configuring with `Apollo exited before its serverinfo API became ready`, take it.**

## A correction to 0.6.8

The 0.6.8 notes said that seats no longer need `C:\Program Files\ApolloVibe\config\apps.json` to
exist, because each seat now reads its own copy. That was not enough, and the fix did not work on a
clean install.

## What was happening

Apollo touches its own install directory twice before it reads any setting from a seat's
`sunshine.conf`. First, it creates `config\` inside the install directory if that folder is missing.
Second, it copies `assets\apps.json` to `config\apps.json` if that file is missing.

Both steps use Apollo's built-in default path. The per-seat `file_apps` setting that 0.6.8 added is
applied only after both, so it could not help.

A seat runs Apollo as a standard Windows user, and a standard user cannot write under
`C:\Program Files`. On an install where the folder or the file was missing, Apollo failed before its
log file was open, waited about ten seconds and exited. Nothing was written, which is why there was
no seat log to read.

The ApolloVibe release zip ships no `config\` folder. So every clean install started in that state,
until someone ran Apollo once with administrator rights.

## What changes

**The service now prepares the install directory before every Apollo launch.** It runs as SYSTEM, so
it can do what a seat cannot. It creates `config\` if that folder is missing. It then copies
`assets\apps.json` to `config\apps.json` if that file is missing.

**It never overwrites an existing `apps.json`.** Once Apollo or you have written one, it is left
alone.

**The copy is atomic.** The file is copied to a uniquely named temporary file in the same folder and
then moved into place without overwrite. A seat that starts at the same moment never reads a
half-written file. The temporary file is always removed.

**It never creates the install directory itself.** If ApolloVibe is not installed, the service logs
a warning and creates nothing.

**A failure to seed is logged as a warning and the launch goes ahead.** The readiness check still
reports the seat's error if Apollo does not start.

**`install-prerequisites.ps1` does the same.** It creates the folder and seeds `apps.json` at
install time, again without overwriting.

Because the seed runs first, a seat's own `apps.json` is now copied from the seeded file, so a first
provision on a clean install gets an app list too.

## Who this affects

- Anyone on a clean install, or any host where `C:\Program Files\ApolloVibe\config\apps.json` does
  not exist. These seats failed before, and should now start.
- Nothing changes on a host that already has that file.

## One edge case

If your host has a curated standalone `C:\Program Files\Apollo\config\apps.json` and no
`config\apps.json` in the ApolloVibe folder, seats will now get the shipped default app list
instead. The seed creates the ApolloVibe file first, so the seat copies that one.

To keep your list, copy it into `<ApolloRoot>\config\apps.json` before you upgrade. By default that
is `C:\Program Files\ApolloVibe\config\apps.json`. A file that is already there is never replaced.

## If you are hitting this today

The workaround still works on any version and does not need this release. From an elevated
PowerShell:

```powershell
New-Item -ItemType Directory -Force "C:\Program Files\ApolloVibe\config" | Out-Null
Copy-Item "C:\Program Files\ApolloVibe\assets\apps.json" "C:\Program Files\ApolloVibe\config\apps.json"
```

Then tear the seat down and provision it again.

## Pair it with ApolloVibe v2026.6.1-ms4

Failures like this one were silent partly because Apollo exited before it logged anything, and it
exited with code 0 as if nothing had gone wrong. ApolloVibe `v2026.6.1-ms4` changes that. When
startup config fails early, Apollo now writes `sunshine-startup-error.log` next to the executable,
or in the temp directory if that folder is not writable, and exits with code 2. This is tracked in
ApolloVibe issue #3.

This release works with the older ApolloVibe too. The newer one makes any remaining early failure
visible.

## How this was checked

The new tests cover the seeding. They check that a missing folder and file are created and seeded,
that an existing `apps.json` is never replaced, that a missing install directory is reported and
nothing is created, that a missing source is reported, that no temporary files are left behind, and
that an IO failure is reported as a warning. All 582 unit tests pass, and the Release build has 0
warnings.

Host check: run on a real host on 2026-09-25 with `C:\Program Files\ApolloVibe\config` removed, which reproduces the clean-install state. On 0.6.9, provisioning a seat failed: Apollo exited about 12 seconds after launch and the API answered 400 "Apollo exited before its serverinfo API became ready". On 0.6.10, the service created the folder and seeded `apps.json` (identical to `assets\apps.json`), Apollo stayed up, its `serverinfo` answered, and the seat reached Ready in 14 seconds. The seat was torn down cleanly and the original folder was restored.

Not tested: streaming to a client, and a fresh install from the ApolloVibe release zip. The folder was removed by hand to simulate one.

## Install

```powershell
.\prerequisites\install-prerequisites.ps1     # drivers - needed either way
.\scripts\install-service.ps1 -FromZip .
```

Your configuration is preserved, as of 0.6.4 — `appsettings.json` and `appsettings.local.json` are
kept byte for byte, with a backup under `C:\ProgramData\MultiSeat\config-backups\`.

Afterwards, confirm what landed:

```powershell
& 'C:\Program Files\MultiSeat\MultiSeat.Service.exe' --config
```

It should report `0.6.10`.

## Known limitations

- **Seats capture the remote desktop surface, not a dedicated virtual display.** A Windows
  constraint on where a virtual display can attach, not a regression.
- **The seat refresh rate is one value for the whole host**, not one per seat.
- **Tearing a seat down still briefly disturbs a standalone Apollo.**
- **An Apollo that dies before it starts logging can still explain nothing** unless you run the
  ApolloVibe build named above.
