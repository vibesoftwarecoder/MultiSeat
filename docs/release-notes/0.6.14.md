**This release adds a dashboard control for a seat's DPI scale, cleans up a deleted account's Windows profile and registry entry, and fixes a dependency advisory in the dashboard's build tooling.**

## What was happening

Three separate things prompted this release.

Issue #70 had one piece left after 0.6.12: a seat's DPI scale override could only be set through the API, not the dashboard. Issue #77: deleting a seat account through the API removed the Windows account but left its profile directory under C:\Users\<name> and its ProfileList registry entry behind, permanently. And a high-severity advisory landed in brace-expansion, a transitive dependency of the dashboard's dev and lint tooling.

## What changes

**A dashboard control for a seat's DPI scale (closes the rest of #70).** Setting a seat's display scale used to need an API call. It's now a dropdown on the New Seat form (defaulting to Auto, unchanged behavior) and a live control on the seat card, matching how resize already works. No backend changed; the API this drives already existed.

**Deleting an account now removes its Windows profile too (#77).** Before this, deleting a seat account through the API removed the Windows account but left its profile directory under C:\Users\<name> and a ProfileList registry entry behind, permanently. Both are now cleaned up when the account is deleted, using the same mechanism (Win32_UserProfile) that's been used by hand to clean up test accounts all along. A profile that's missing (never logged into) or still in use is handled gracefully with a warning, not a crash.

**A dependency fix.** A high-severity advisory in a transitive dev/lint dependency (brace-expansion) was fixed. It never shipped to end users - this only affects the dashboard's build tooling.

## Who this affects

For the scale control: anyone who wants a custom DPI scale without using the API directly - the iPad Pro/tablet case from #70 originally. For the profile cleanup: anyone who creates and deletes seat accounts through the API and was accumulating stale profile folders. For the dependency fix: nobody functionally, this is a supply-chain hygiene fix.

## How this was checked

For the scale control, it was live-verified end to end on a real host: creation-time scale, a live change, and clearing it back to Auto, each confirmed in the API response and the seat's actual Default.rdp file, with the seat staying Ready throughout. The known limitation carried over from #70 still stands: whether Windows actually applies a new scale to a session it reconnects to, as opposed to a freshly created one, has still never been confirmed by a real Moonlight client - only that the service correctly records and writes the value.

For #77, it was live-verified on a real account created through the normal API flow, not just a synthetic test: the Windows account, its profile directory, and its ProfileList registry entry were all confirmed gone after deletion.

For the dependency fix, `npm audit` (any severity) now reports 0 vulnerabilities, and the dashboard build still succeeds.

A related gap was found along the way and filed separately as #80, not fixed here: a brand-new seat account's first-run "Microsoft account" screen can block a seat from provisioning until the account has logged in once.

## Install

```powershell
.\prerequisites\install-prerequisites.ps1     # drivers - needed either way
.\scripts\install-service.ps1 -FromZip .
```

Your configuration is preserved, as of 0.6.4 — `appsettings.json` and `appsettings.local.json` are
kept byte for byte, with a backup under `C:\ProgramData\MultiSeat\config-backups\`.

Afterwards, confirm what landed:

```powershell
& 'C:\Program Files\MultiSeat\MultiSeat.Service.exe' --config
```

It should report `0.6.14`.

## Also in this release

Everything from 0.6.13, including the host refresh-rate setting and the rejection of blank account passwords. See the [0.6.13 notes](0.6.13.md).

## Known limitations

- **Seats capture the remote desktop surface, not a dedicated virtual display.** A Windows
  constraint on where a virtual display can attach, not a regression.
- **The seat refresh rate is one value for the whole host**, not one per seat.
- **Tearing a seat down still briefly disturbs a standalone Apollo.**
- **An Apollo that dies before it starts logging can still explain nothing** unless you run
  ApolloVibe `v2026.6.1-ms4` or later, which writes `sunshine-startup-error.log` on an early
  startup failure.
- **A brand-new seat account's first-run "Microsoft account" screen can block a seat from
  provisioning** until the account has logged in once. Filed as #80, not fixed here.
