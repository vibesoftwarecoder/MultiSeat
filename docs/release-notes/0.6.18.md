**This release makes a seat wait for its Windows session to be usable before starting Apollo, so a slow or locked-down logon no longer makes a new seat fail.**

## What was happening

Issue #96: on one host, a freshly created seat failed to start Apollo. Apollo logged `Failed to Open Input Desktop [0x00000005]` and then `DuplicateOutput() test failed [0x80070005]`, and the seat was torn down. Reconnecting the same session made it work.

The reporter traced it to a third-party logon task that switches to the Secure Desktop right after logon. The session's input desktop opened once, was then denied for about two minutes, and came back by itself. Apollo's first startup probe ran inside that window and failed, and MultiSeat gave up on Apollo after 30 seconds.

## What changes

- **MultiSeat now waits inside the seat's session until the input desktop has stayed openable for 3 seconds in a row**, then starts Apollo. It gives up after 180 seconds and starts Apollo anyway, with a warning, as it did before. Set `WaitForInputDesktopSeconds` to `0` to turn the wait off. `InputDesktopStableMs` sets the 3-second window.
- **`ApolloReadinessTimeoutSeconds`** makes the 30-second Apollo readiness timeout configurable. The default is still 30.
- **A warning when a Ready seat has no working encoder.** If Apollo answers `/serverinfo` but its own log says it found no working encoder at startup, the service log now carries a Warning with that line and the log path. The seat's status does not change. `Ready` still does not promise that capture is working. Capture only starts when a client connects.
- **A diagnostic for this class of problem (off by default).** `MultiSeat:DiagnoseInputDesktopReadiness` samples the input desktop and lists every desktop and window in the session, writing a timestamped JSONL file. `POST /api/seats/{id}/diagnostics/input-desktop-probe` runs it against a seat that is already live, and `scripts/diagnose-issue96.ps1` runs repeated trials. Nothing here runs unless you turn it on.
- **Dashboard dependency fix.** `source-map-js` is bumped to 1.2.2, clearing a high-severity denial-of-service advisory (#98).

## Who this affects

Anyone whose seat fails to start Apollo right after logon with an access-denied error on the input desktop, especially on a host with a logon task that raises a Secure Desktop prompt. If your seats already start cleanly, nothing changes, except that a start may wait up to a few seconds longer while the desktop settles.

## How this was checked

CI passes on `master`, including the new tests for the wait and for the log scan. The reporter ran the change on the affected host with its logon task left enabled. One fresh seat waited 126 seconds, started Apollo on the first attempt with no reconnect, and streamed to a Moonlight client with no mouse bleed.

**What this doesn't confirm:** that is one run on one host. It does not show the failure is gone for good, and the bug has not reproduced on any other host. If you see it again, please comment on #96 with the seat's Apollo log.

## Known limitations

- **Seats capture the remote desktop surface, not a dedicated virtual display.** A Windows constraint, not a regression.
- **The seat refresh rate is one value for the whole host**, not one per seat.
- **The keyboard/mouse isolation setting is still a known no-op** — see #92's thread for the current understanding.
- **`Ready` does not mean capture is active.** Capture begins when a client connects.
- **A seat's explicit scale setting can be lost after a client-triggered resolution change** (#93, open).
