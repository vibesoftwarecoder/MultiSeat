**A dependency and diagnostics release. Update it, but do not panic about it — the security fixes
are real and none of them were exploitable in this dashboard.**

## Dependencies

`npm audit` on the dashboard reported **11 vulnerabilities, 8 of them high**. All 11 are now
cleared. `react-router` went from 7.14.0 to **7.18.3**, and 31 other packages moved by a patch or
minor version.

Nothing in `package.json` changed. Every one of the 32 updates sits inside a semver range the
project already declared, so no dependency was upgraded across a breaking boundary.

**On exposure, plainly.** Two of the advisories were reported to us as high-severity remote code
execution and cross-site scripting. Neither applies here. `CVE-2026-42211` requires React Router's
Framework Mode and `CVE-2026-33245` requires its unstable React Server Components APIs; this
dashboard uses neither — it is a plain Vite single-page app on `<BrowserRouter>`. The one advisory
in the set that *does* reach an app built this way is an open redirect through `<Link>` and
`useNavigate`, and it has nowhere to land: every navigation target in the dashboard is a hardcoded
string, and `useNavigate` is not used at all.

So this is hygiene, not an incident. It is still worth taking, because the next advisory may not be
so conveniently out of scope, and because the dashboard now gets checked.

**The dashboard is now built and audited by CI on every pull request.** It never was before, which
is how 11 advisories accumulated without anyone noticing. A high-severity finding now fails the
build rather than printing a warning nobody reads.

`pnpm-lock.yaml` has been deleted. Nothing used it — the installer runs `npm install` — and it had
drifted two minor versions away from the lockfile that is actually used.

## Seats now say why they failed

Every seat is an RDP session. If RDP Wrapper is inactive, no seat can start, ever. Until now
nothing said so.

`install-service.ps1` checked for the virtual display driver and the audio cables but not for RDP
Wrapper, so it would install and start the service on a host where seats were impossible. The first
sign you got was a seat timing out, and the timeout listed refreshing `rdpwrap.ini` as one
suggestion among four — alongside three others that cannot help while the wrapper is inactive.

Two changes:

**The installer checks before it installs.** It detects both ways RDP Wrapper can be installed, and
it separates *not installed* from *installed but not covering this Windows build*. The second is
the one you cannot see from the outside: a Windows update replaces `termsrv.dll`, the offsets in
`rdpwrap.ini` no longer match, and the wrapper sits there looking fine while doing nothing. The
verdict is repeated at the very end of the install, after the success message, because a warning
several screens up is a warning nobody sees.

**The seat timeout names the cause.** It now asks whether multi-session RDP actually works before
listing remedies. If it does not, the error says so first and points at `check-rdpwrap-offsets.ps1`,
which can compute the right offsets locally rather than waiting for the community `rdpwrap.ini` to
add your build. If the wrapper is fine, the error says that too and drops the steps that no longer
apply.

Reported by @darkjezza in #33, and by @begininvoke in #34 and #35.

## Install

Download `multiseat-windows-x64.zip`, extract it anywhere, and run both scripts from inside the
extracted folder:

```powershell
.\prerequisites\install-prerequisites.ps1     # drivers - needed either way
.\scripts\install-service.ps1 -FromZip .
```

Still self-contained: no clone, no .NET SDK, no .NET runtime, no Node. `-FromZip` accepts either
the extracted folder, as above, or the `.zip` itself.

If you are upgrading from 0.6.1 and seats already work, the prerequisite script is not required
again — but running it is harmless and is what refreshes `rdpwrap.ini` after a Windows update.

## Still true from 0.6.1

- The version comes from one file. A `v*` tag that disagrees with `version.txt` fails the release.
- `& 'C:\Program Files\MultiSeat\MultiSeat.Service.exe' --config` reports the deployed version,
  commit and resolved settings. Worth running before reporting a bug.
- The installer never writes `scripts`, `prerequisites` or `README.md` into `C:\Program Files`, and
  never deletes the folder you extracted.
- Keyboard/mouse isolation (`EnableKeyboardMouseIsolation`) is off by default and remains a no-op.

## Known limitations

- **The new RDP Wrapper checks have not been run on a host that is actually in the broken state.**
  Reproducing that needs a machine whose `rdpwrap.ini` does not cover its `termsrv.dll`, and we do
  not have one. The logic mirrors the check the service already performs, and CI builds and lints
  it, but that is not the same as watching it fire. If you hit the new warning and it is wrong,
  please open an issue.
- The `-FromZip` install path still has not been run on a fresh host.
