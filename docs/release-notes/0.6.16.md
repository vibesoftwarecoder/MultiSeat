**This release recovers a seat automatically after the service restarts, the host resumes from sleep/hibernate, or a session is reused by a different account.**

## What was happening

Issue #87: a seat (and its RDP account/profile) never survived anything happening to the MultiSeat service itself — a crash, an update, a restart — because nothing auto-recreated it. Nor did it survive the host sleeping or hibernating, since no mechanism existed to detect a resume and recheck seat health. Separately, Windows reuses RDP session numbers, and the service had no way to tell "this session number is active" from "this session number is active and still belongs to our seat."

## What changes

Four parts, building on each other.

**Auto-start is now offered at seat creation**, not just settable after the fact. A new toggle on the dashboard's New Seat form and seat card controls whether a seat's configuration is saved as a preset that survives a restart. Existing API callers are unaffected — omitting the field changes nothing; only explicitly turning it off removes a saved preset.

**A session's actual owner is checked, not just its session number.** Windows reuses RDP session numbers. The health check and teardown logic now also check the account name behind a session before treating it as "ours" — so a reused session number under a different owner goes to Error instead of being disconnected or logged off.

**Seats with auto-start now recover after the service restarts or the host resumes from sleep/hibernate.** On service startup, any seat with a saved preset is automatically reprovisioned, retrying up to 3 times (15s/30s backoff) if needed. The service also registers for Windows power-event notifications and triggers the same recovery on resume. Independently of both, the regular health check also triggers recovery whenever it notices a seat's session has disappeared — so recovery doesn't strictly depend on catching the resume event.

**Docs** cover enabling auto-start and a new troubleshooting entry for "a seat is gone after a restart, a reboot, or hibernation."

## Who this affects

Anyone who wants a seat to still be there after MultiSeat itself restarts or the host sleeps — previously this required manually noticing and recreating the seat.

## How this was checked

778 tests pass, 0 failures, mutation-checked — each fix reverted, confirmed its test fails, restored.

**Live-verified on the real host, not just built.** Deployed the build and restarted the service: the Event Log shows Gaming's seat (torn down by the old service's shutdown) was automatically reprovisioned and reached Ready in about 19 seconds, on the first attempt. Exercised the full auto-start lifecycle end-to-end on a throwaway seat — create with auto-start on, confirm the preset file, toggle it off, confirm the preset is removed, delete the seat and account, confirm full cleanup. Gaming itself was never touched and stayed Ready throughout.

**What this doesn't confirm:** the resume-from-hibernate path specifically. The host wasn't put to sleep during testing, and a direct check of the service's power-event registration was inconclusive. The service-restart recovery path above is fully proven; the resume-specific trigger is unproven but has a working fallback — the health check will eventually catch a vanished session and recover it either way, just not as immediately as a resume event would.

## Install

```powershell
.\prerequisites\install-prerequisites.ps1     # drivers - needed either way
.\scripts\install-service.ps1 -FromZip .
```

Your configuration is preserved, as of 0.6.4 — `appsettings.json` and `appsettings.local.json` are
kept byte for byte, with a backup under `C:\ProgramData\MultiSeat\config-backups\`.

Afterwards, confirm what landed:

```powershell
& 'C:\Program Files\MultiSeat\MultiSeat.Service.exe' --config
```

It should report `0.6.16`.

## Known limitations

- **Seats capture the remote desktop surface, not a dedicated virtual display.** A Windows
  constraint on where a virtual display can attach, not a regression.
- **The seat refresh rate is one value for the whole host**, not one per seat.
- **Tearing a seat down still briefly disturbs a standalone Apollo.**
- **The resume-from-hibernate auto-recovery trigger is unconfirmed on this host** (see above); the health-check fallback is confirmed.
